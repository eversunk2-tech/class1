# admin-purge-oauth-member (Edge Function)

관리자 화면(`/admin/members/`)에서 **구글·깃허브(OAuth)로만 로그인하는 계정**의 **완전 삭제** 메뉴가 호출하는 함수입니다.
총괄 관리자만 쓸 수 있고, 로그인 계정뿐 아니라 그 계정의 **기록까지 모두** 지워 대시보드에 남지 않게 합니다.
설계: `docs/admin/oauth-delete/spec.md`(끝 "개정 1 — 사용자 결정"이 우선).

> **되돌릴 수 없습니다.** 복구 기능은 없습니다. 같은 구글·깃허브 계정으로 다시 로그인하면 **새 계정**(새 id, 일반 회원, 학급 없음)으로 시작합니다.

아이디(`아이디@class1.local`)로 로그인하는 계정은 이 함수의 대상이 아닙니다 — 지금처럼 **탈퇴 처리**(`admin-delete-member`, 기록 보존)를 씁니다.

## 누가 · 누구를

- **총괄**(`profiles.role = 'admin'` + `is_super_admin = true`)만 쓸 수 있습니다. 담임은 **403** "구글·깃허브 계정의 완전 삭제는 총괄 관리자만 할 수 있습니다."
  (구글·깃허브로 가입한 계정은 학급이 없어 원래 담임의 관리 대상이 아닙니다.)
- 대상은 **학생(일반 회원) 역할이면서 아이디 로그인이 없는 계정**입니다. 회원 명단(`member_directory.provider/providers`)과
  로그인 계정(`auth.users`의 identities·app_metadata)으로 **두 번** 확인하고, 아이디 로그인이 하나라도 있으면 **400**으로 거부합니다.
- **교사(관리자) 계정은 400** "교사(관리자) 계정은 먼저 담임 해제를 해 주세요." — 총괄이 먼저 **담임 해제**를 한 뒤 완전 삭제합니다.
  (담임 해제는 학생이 있는 학급을 혼자 맡고 있으면 거부됩니다 — 학급을 먼저 넘기거나 비웁니다.)
- 예전에 **탈퇴 처리**한 구글·깃허브 계정("탈퇴함")도 같은 메뉴로 남은 기록을 지울 수 있습니다(자동 일괄 삭제는 없음 — 하나씩).

## 순서 (다시 눌러도 안전)

1. 호출자 로그인 확인 → 2. 총괄 확인 → 3. 대상 확인(자기 자신·교사·아이디 계정 거부) → 4. 새 SQL 적용 확인 — **여기까지는 아무것도 지우지 않습니다.**
5. Storage `game-uploads`의 `{회원 id}/` 폴더(올린 게임 파일)를 모두 지우고 비었는지 다시 확인합니다. 실패하면 여기서 멈춥니다(로그인 계정·기록은 그대로).
6. 로그인 계정(`auth.users`)을 **하드 삭제**합니다(이미 없으면 건너뜀).
7. DB 함수 `admin_purge_oauth_member`(서비스 롤 전용)가 남은 기록을 **한 트랜잭션으로** 지웁니다.
   7이 실패하면 "…아직 지우지 못했습니다. 한 번 더 실행하면 남은 기록만 다시 지웁니다" 경고와 함께 200을 돌려줍니다 —
   같은 회원에게 **완전 삭제**를 한 번 더 누르면 5·6은 "이미 없음"으로 통과하고 7만 다시 합니다.

## 지워지는 것 / 남는 것

| | |
|---|---|
| **지워집니다** | 로그인 계정(구글·깃허브 연결, 세션), 프로필·회원 명단, 웹앱 결과·진행 상황·읽은 글·과제 제출·피드백 대화, 블로그 댓글·좋아요, 자유게시판·학습게임에 쓴 글(**그 글에 달린 다른 사람의 댓글·좋아요도 함께**)·댓글·좋아요·한 신고, 그 계정의 글·댓글을 신고한 기록, 올린 게임 파일, 관리 기록(탈퇴·계정 생성·비밀번호 초기화 기록에서 그 계정 행). 교사였던 계정이면 **학생에게 보낸 피드백·칭찬 메시지도** 함께 지워집니다. |
| **남습니다(쓴 사람만 비워짐)** | 교사였던 계정이 쓴 선생님 글·과제·블로그 글·칭찬 문구·만든 학급 — 쓴 사람이 비어 **총괄만** 고치고 지울 수 있습니다. 그 교사가 처리한 다른 회원의 관리 기록은 남되 처리한 사람 이름·id는 비웁니다. |
| **남기지 않음** | "누가 언제 완전 삭제했는지" 기록(사용자 결정 — 개정 1 Q3). 함수 로그에도 성공은 남기지 않고, 실패한 단계와 오류 문구만 남깁니다(이메일·이름·토큰 없음). |

- 이미 로그인해 둔 기기의 접근 토큰은 만료(기본 1시간)까지 잠깐 유효할 수 있습니다(다른 관리 함수와 같은 한계). 그동안 새 글·기록은
  프로필이 없어 저장되지 않지만, 게임 파일 업로드(Storage)는 이론상 들어갈 수 있습니다 — 걱정되면 한 시간 뒤 Supabase 대시보드
  Storage > `game-uploads`에서 그 id 폴더가 비었는지 보세요.

## 먼저 할 일 (순서)

1. Supabase SQL Editor에서 **`supabase/migrations/20260928000000_oauth_purge.sql`을 실행**하고 파일 위의 확인 쿼리 1)·2)를 봅니다.
   - 실행하지 않은 상태에서는 이 함수가 "완전 삭제 기능용 DB 설정이 아직 적용되지 않았습니다"로 거부합니다(아무것도 지우지 않음).
2. 이 함수를 배포합니다(아래). 다른 함수 4개는 바뀌지 않아 다시 배포할 필요가 없습니다.
3. 사이트를 배포(push)합니다.

## 환경·설정

- 환경변수 `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`는 Supabase가 자동으로 넣어 주므로 **따로 설정할 필요가 없습니다.**
- 허용 출처(CORS): `https://eversunk2-tech.github.io`, `http://localhost:3000` + Supabase Secrets **`EXTRA_ALLOWED_ORIGINS`**(지금 Vercel 주소 — 다른 함수와 같은 Secret을 읽습니다. 새로 설정할 것 없음).
- **JWT 검증(Verify JWT)은 켜 둔 상태(기본값)로 배포하세요.**

## 방법 A: Supabase CLI로 배포 (사용자 Mac 터미널)

```bash
npx supabase functions deploy admin-purge-oauth-member
```

(`--no-verify-jwt`를 붙이지 마세요. "Access token not provided"가 나오면 `npx supabase login`부터 — 브라우저 승인 → 확인 코드.)

## 방법 B: 대시보드 에디터로 배포 (CLI 없이)

1. Supabase 대시보드 → 프로젝트 선택 → 왼쪽 메뉴 **Edge Functions**.
2. **Deploy a new function** → **Via Editor**.
3. 함수 이름을 정확히 `admin-purge-oauth-member`로 입력합니다(화면 코드가 이 이름으로 호출합니다).
4. 예제 코드를 모두 지우고 이 폴더의 `index.ts` 내용을 그대로 붙여 넣습니다.
5. **Deploy function**을 누르고, **Settings**에서 **Verify JWT**가 켜져 있는지 확인합니다.

## 배포 후 확인 (실제 시험용 계정으로)

1. **완전 삭제해도 되는 시험용** 구글(또는 깃허브) 계정으로 사이트에 로그인해 가입합니다(자동으로 일반 회원). 자유게시판에 글·댓글을 하나 남겨 봅니다.
2. 총괄 계정으로 **회원 관리**에서 그 계정을 찾습니다 — `⋮` 메뉴에 **탈퇴 처리** 대신 **완전 삭제**가 보여야 합니다.
   회원 상세를 열어 주소의 `id=…` 값을 적어 둡니다(확인 쿼리용).
3. **완전 삭제** → 이름을 그대로 입력 → 실행. 목록에서 그 행이 사라져야 합니다.
4. SQL 파일 위의 **확인 쿼리 3)**에 적어 둔 id를 넣어 실행 — 모두 0이어야 합니다. 자유게시판에서 그 글도 사라졌는지 봅니다.
5. 로그아웃한 뒤 **같은 구글(깃허브) 계정으로 다시 로그인** — 새 계정으로 가입되어야 하고, 예전 글·기록은 보이지 않아야 합니다.
   **확인 쿼리 4)**로 새 id(적어 둔 id와 다름)·역할 user·학급 없음을 봅니다.
6. 아이디 계정(학생)의 `⋮` 메뉴는 그대로 **탈퇴 처리**인지 봅니다.
