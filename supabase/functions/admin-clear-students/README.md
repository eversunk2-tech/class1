# admin-clear-students (Edge Function)

관리자 화면의 **[학급 정리]**(학급 카드)와 회원 메뉴의 **[기록까지 삭제]**가 부르는 함수입니다.
학생 계정과 그 학생의 **모든 기록**을 지웁니다 — 기존 '탈퇴 처리'와 달리 **"탈퇴한 학생"으로도 남지 않고, 되돌릴 수 없습니다.**
설계: `docs/privacy/spec.md` 4.7-3 · 4.11(개정 4 — 가린 이름 확인) · 5절(머리말 개정 1~4와 1.1 결정표가 본문보다 우선). 화면 글은 `docs/privacy/privacy-policy.md` 8-4 · 8-5.

| 모드 | 요청 | 쓰는 때 |
|---|---|---|
| 학급 정리 | `{ "classId", "confirmName": 학급 이름 }` | 학년도가 끝난 뒤(종업식 뒤 그 학년도의 2월 28일까지) 그 학급 학생 모두 — **탈퇴 처리된 학생 포함** |
| 학생 한 명 | `{ "userId", "confirmName": 학생 이름 }` | 보호자·학생이 삭제를 요구할 때(법 제36조, 처리방침 제6조) |

> Supabase 무료 요금제라 **백업이 없습니다**(spec R19). 화면은 이름 입력 + "되돌릴 수 없음" 확인을 거칩니다. 종이 보호자 동의서도 함께 파쇄합니다.

## 누가 · 누구를

- 호출자: 관리자(`profiles.role = 'admin'`). 학급 정리는 **그 학급의 담임**(`class_teachers`) 또는 **총괄**, 학생 한 명은 **그 학생의 담임** 또는 **총괄**
  (학급이 없는 학생은 총괄만). 그 밖에는 403. 교사 인증 코드로 시작한 구글 선생님(`teacher_scope = 'class'`)도 자기 학급은 정리할 수 있습니다(학급 안 일).
- 대상: `role = 'user'`이고 **구글·깃허브 전용이 아닌 계정**(아이디로 로그인하는 학생). 구글·깃허브 전용 계정은 지우지 않습니다(총괄의 **완전 삭제**를 씁니다 —
  학급 정리에 섞여 있으면 건너뛰고 `failed`로 세며 `warning`으로 알립니다). 회원 명단으로 가입 방식을 알 수 없으면(명단 줄 없음 등) 로그인 계정으로
  한 번 더 보고, 구글·깃허브 전용이 아니면(로그인 계정이 없는 탈퇴한 학생 포함) 지웁니다 — DB 함수 `admin_purge_class_member`와 같은 규칙
  (학급 정리가 영영 끝나지 않는 일을 막음). 교사 계정·자기 자신은 지우지 않습니다.
- `confirmName`: 학급 이름 / 학생 이름(화면에 보이는 이름 — 표시 이름, 없으면 로그인 아이디)과 **앞뒤 공백을 뺀 뒤 똑같아야** 합니다. 다르면 400 `confirm_mismatch`.
  - **가린 이름(spec 4.11 개정 4)**: 총괄이 **담임이 아닌 다른 학급 학생**을 지울 때는 회원 명단에 보이는 대로 **가린 이름**(원래 이름의 첫 글자 + `***`, 예 `2***` — 원래 이름이 비었으면 `***`)을 적습니다. 함수가 SQL ①의 `mask_label(privacy_name_source(표시 이름, 아이디))`와 같은 규칙(앞뒤 공백은 JS `trim()`과 같은 글자, 첫 글자는 코드 포인트 하나)으로 만들어 비교합니다. 그 학생의 담임(총괄이 담임을 겸하면 총괄도)과 학급 없는 학생을 지우는 총괄은 지금처럼 원래 이름을 적습니다.
- **지우지 않는 것**: 학급(이름), 선생님 글, 과제(내용), 선생님 계정, 칭찬 문구.

## 순서 (다시 눌러도 안전)

권한·이름·새 SQL(`admin_purge_class_member`가 있는지) 확인 — **여기까지는 아무것도 지우지 않습니다.** 그다음 학생마다:

1. Storage `game-uploads`의 `{학생 id}/` 폴더(올린 게임 파일)를 지우고 비었는지 다시 확인 — **실패하면 그 학생은 건너뜁니다**(계정·기록 그대로, `failed`).
2. 로그인 계정(`auth.users`)을 하드 삭제 — 이미 없으면(탈퇴한 학생·다시 누름) 통과. 다른 오류면 건너뜁니다(`failed`).
3. DB 함수 `admin_purge_class_member(p_target, p_actor)`(서비스 롤 전용)가 남은 기록을 한 트랜잭션으로 지웁니다. 실패하면 `failed` —
   다시 누르면 1·2는 통과하고 3만 다시 합니다.

- **학급 정리는 한 번에 20명씩** 처리합니다(시간 제한 안에서 끝나게). 그 학급 학생을 id 순으로 살펴 **지울 수 없는 학생(구글·깃허브 전용 등)은 건너뛰고** 그 뒤 학생으로 넘어가므로, 그런 학생이 앞에 몰려 있어도 같은 학생만 되풀이하지 않습니다(고침 1 — 검토 R1 L7). 건너뛴 학생은 `failed`에 들어갑니다. 화면은 `remaining`이 0이 될 때까지 다시 부르고("`{done}`/`{total}`명 정리했어요…"),
  한 번에 하나도 못 지우면(`deleted = 0`) 멈추고 "{k}명을 지우지 못했어요. 다시 [학급 정리하기]를 눌러 주세요."를 보입니다.
- **학급 정리 기록**: 1명 이상 지운 호출마다 `admin_finish_class_cleanup(학급, 호출자, 이번에 지운 수)`를 부릅니다. DB 함수가 같은 학급·같은 선생님의
  1시간 안 기록에 더하므로 20명씩 여러 번 불러도 **한 번의 정리 = 한 줄(인원수만)** 입니다(학생 이름·아이디 없음 — 질문 11).
  빈 학급에 다시 눌러도 기록이 늘지 않습니다. 중간에 멈췄다면 그때까지 지운 인원수가 남습니다.
- 로그에는 실패한 단계와 오류 문구만 남깁니다(토큰·이메일·이름·id 없음, 오류 문구 안의 id·이메일 모양도 가림). 성공은 남기지 않습니다.

## 응답

```jsonc
// 200 — 두 모드 같은 모양
{ "ok": true, "deleted": 20, "failed": 0, "remaining": 6 }
// 학급에 구글·깃허브 계정이 섞였거나 학급 정리 기록을 못 남겼을 때만 warning
{ "ok": true, "deleted": 2, "failed": 1, "remaining": 1, "warning": "구글·깃허브로 로그인하는 계정 1개는 학급 정리로 지울 수 없습니다. …" }
// 학생 한 명: 기록 단계만 실패(계정·파일은 지움) — 같은 학생에게 다시 하면 기록만 다시
{ "ok": true, "deleted": 0, "failed": 1, "remaining": 1, "warning": "로그인 계정과 올린 게임 파일은 지웠지만 기록을 아직 지우지 못했습니다. …" }
```

| 상태 | 본문 `error`(+`code`) | 뜻 |
|---|---|---|
| 400 | "학급 이름이 맞지 않습니다…" / "이름이 맞지 않습니다…" (`confirm_mismatch`) | 이름 확인 실패 — 지운 것 없음 |
| 400 | "학급 정리 기능용 DB 설정이 아직 적용되지 않았습니다. …20261020000000_privacy_a_schema.sql…" | SQL ① 전 — 지운 것 없음 |
| 400 | "교사(관리자) 계정은 이 메뉴로 지울 수 없습니다." / "구글·깃허브로 로그인하는 계정은 … '완전 삭제'를 이용하세요." / "자기 자신의 계정은 지울 수 없습니다." | 대상이 맞지 않음 |
| 400 | "요청 형식이 올바르지 않습니다…" | `classId`와 `userId`를 둘 다 보내거나 둘 다 안 보냄 |
| 401 | "로그인이 필요합니다." / "로그인이 만료되었습니다…" | |
| 403 | "관리자만 사용할 수 있습니다." / "이 학급의 담임 선생님이나 총괄 관리자만 학급 정리를 할 수 있습니다." / "이 학생의 담임 선생님이나 총괄 관리자만 기록까지 삭제할 수 있습니다." | 권한 없음(없는 학급도 담임에게는 같은 403) |
| 404 | "학급을 찾을 수 없습니다." (`class_not_found`) / "대상 계정을 찾을 수 없습니다…" (`target_not_found`) | 이미 지워짐 — 화면은 목록을 새로 불러옴 |
| 500 | "올린 게임 파일을 지우지 못해 멈췄습니다…" 등 | 잠시 뒤 다시(학생 한 명 모드 — 지운 것 없음) |

## 먼저 할 일 (순서 — spec 7절)

1. Supabase SQL Editor에서 **`supabase/migrations/20261020000000_privacy_a_schema.sql`(SQL ①)** 실행 + 파일 위 확인 쿼리.
2. 이 함수를 배포합니다(아래). `member-self-delete`·`admin-create-member`도 함께.
3. 사이트를 배포(push)합니다.

## 환경·설정

- 환경변수 `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`는 Supabase가 자동으로 넣어 주므로 **따로 설정할 필요가 없습니다.**
- 허용 출처(CORS): `https://eversunk2-tech.github.io`, `http://localhost:3000` + Supabase Secrets **`EXTRA_ALLOWED_ORIGINS`**(다른 함수와 같은 Secret — 새로 설정할 것 없음).
- **JWT 검증(Verify JWT)은 켜 둔 상태로 배포하세요**(`supabase/config.toml`에 `verify_jwt = true`).

## 배포 (사용자 Mac 터미널)

```bash
npx supabase functions deploy admin-clear-students
```

(`--no-verify-jwt`를 붙이지 마세요.) 대시보드로 배포할 때는 이름을 정확히 `admin-clear-students`로, Settings에서 **Verify JWT** 켜짐 확인.

## 배포 후 확인 (사용자 — 시험용 계정으로)

1. 시험용 학급을 하나 개설하고 시험용 학생 2명을 등록합니다(보호자 동의 체크). 한 명은 '탈퇴 처리'까지 해 둡니다.
2. 그 학급 카드의 **[학급 정리]** → 학급 이름 입력 → 실행 → "정리했어요. 학생 2명의 계정과 기록을 지웠어요." 회원 목록에서 두 학생이 사라졌는지.
3. 같은 [학급 정리]를 다시 눌러 "지울 학생이 없어요"인지(기록이 두 줄로 늘지 않는지).
4. 시험용 학생 한 명을 더 만들고 회원 메뉴 **[기록까지 삭제]** → 이름 입력 → 사라지는지.
5. 함수 로그(대시보드 Edge Functions → admin-clear-students → Logs)에 이메일·이름·id가 없는지.
