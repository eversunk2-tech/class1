## 2. 지침에 없던 것 — 같은 판정을 맞추느라 정한 것

1. **② 백필·점검의 "구글 계정" 판정도 도메인 기준으로 바꿨다.** 대상은 2-1~2-7, 맨 앞 점검 알림, 머리말 A)·C), 끝 점검 6-9·6-10이다. 판정은 `lower(email) not like '%@class1.local'`이고, 이메일·가입 방식 중 하나라도 기록돼 있어야 한다. 트리거와 같은 규칙이어야 다시 실행해도 결과가 같다(가린 `k***`도 아이디 계정이 아닌 쪽으로 남는다). 결과는 다음과 같다.
   - **총괄이 실제 이메일(구글 또는 이메일·비밀번호)로 로그인하면**: 총괄도 회원 명단 이메일이 `e***`로 가려진다. `member_verification('existing')` 줄이 생겨 처음 접속 때 확인 창(3-1)이 한 번 뜬다. 별명을 정할 때까지 이름은 `선생님`이다. 지침의 "총괄도 포함"과 같다.
   - **이미 실제 이메일로 스스로 가입해 있던 계정**(role user, 학급 없음)은 ② 뒤 '인증 전'이 된다.
2. **`handle_new_user`는 아이디 계정도 사진 주소를 null로 만든다.** 예전에는 `user_metadata.avatar_url`을 복사했다. 사용자 결정 "사진 주소 받지 않음"에 맞춘 것이다.
3. **① 3-1 권한 재선언에 다시 실행할 때의 방어를 넣었다.** ②가 적용된 상태(제한 정책 `profiles: 인증 전 쓰기 제한(수정)`이 있음)에서 ①을 다시 Run하면 `grant update (display_name)`만 준다. 처음 실행은 지금 목록 그대로다. 이렇게 해야 "① 다시 실행 안전"이 지켜진다(안 하면 사진 주소 권한이 소리 없이 되살아난다).

## 6. 확인하지 못한 것

- Postgres에서 실제로 실행해 보지 못했다. 특히 ①의 `do` 블록 안 `grant`, `update … from … join`, 끝 점검 쿼리.
- 실 DB에 해당 줄이 있는지 모른다. 구글 관리자 수, 옛 탈퇴 기록의 구글 이메일, 실제 이메일로 스스로 가입한 계정은 머리말 A)·D) 쿼리로 사용자가 볼 수 있다.
- Supabase의 이메일 자가 가입·확인 메일이 실제로 아무 주소에나 가는지(M4)는 공식 문서·대시보드 확인이 필요하다. 이번 고침은 가입이 되더라도 '인증 전'이 되게 막은 것이다.

## 7. 메인 에이전트께

- **배포 순서**: ② 앞에 **'프로필 수정' 창이 별명(display_name)만 보내는 화면**이 배포돼 있어야 한다. 예전 창은 `avatar_url`도 보내 ② 뒤 저장이 42501로 실패한다. 처리방침·화면의 사진 주소 문구도 메인 몫이다.
- **스스로 가입한 실제 이메일 계정(M4)**: ② 뒤 '인증 전'이 되지만 [가입하지 않기]는 실패한다. `member-self-delete`와 ①의 `self_purge_member`가 "구글 전용(가입 방식에 email 없음)"만 받기 때문이고, 오류는 "아이디로 로그인하는 계정은 여기서 지울 수 없어요…"로 나온다. 총괄의 '완전 삭제'(`admin-purge-oauth-member`)도 같은 이유로 막힌다. 지금은 총괄의 '탈퇴 처리'로만 정리된다. 판정을 `@class1.local` 기준으로 넓힐지는 사용자 결정이다(범위 밖이라 고치지 않았다).
- **총괄이 실제 이메일로 로그인하면**(2절 1): ② 직후 총괄 이름이 `선생님`이 되고 확인 창이 한 번 뜬다. 처리방침이나 사용자 안내가 필요하면 반영해 달라.
- **spec 4.4**의 "구글 계정은 이 로그에 들어오지 않는다"는 메인이 고친다(지침대로). **L5**는 spec 4.1 문장만 고치면 된다(3절).
