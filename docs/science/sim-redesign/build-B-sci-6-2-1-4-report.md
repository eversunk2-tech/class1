## 2. 손전등 직접 끌기

`sim3d.js`의 `v.draggable(obj, { plane, onDrag, onEnd })`(단계 A에서 추가)를 손전등(`torch` 그룹)에 연결했다. 손전등은 항상 센서 옆 `(0, SURF, 0)`을 중심으로 `z=0` 평면 위 부채꼴을 도므로, 그 평면과의 교점에서 `atan2`로 각도를 구해 기존 `setAngle(deg)`을 그대로 재사용한다(값은 한 곳에서만 계산 — 슬라이더·눈금 버튼·끌기가 모두 같은 함수를 부른다).

**구현 중 발견한 버그(고침)**: `build3D()`의 `.then(function(v){…})` 콜백 안에는 **3D 장면만 갱신하는 지역 `function setAngle(deg)`**가 이미 있다(장면을 만들 때 `view.setAngle`로 돌려주는 바로 그 함수). 끌기 핸들러를 그 스코프 안에 넣고 그냥 `setAngle(deg)`를 불렀더니 **이름이 가려져 바깥쪽(상태·DOM·저장을 갱신하는) `setAngle(d, now)`가 아니라 이 지역 함수가 불렸다** — 3D 장면은 실시간으로 움직이는데 슬라이더·값 패널·기록 버튼 글자·`angle` 상태는 전혀 안 바뀌는 상태로 몇 차례 테스트가 실패했다(각도가 그대로 45로 남음). 원인을 헤드리스 브라우저로 직접 좁혀 찾았다(포인터 이벤트 발생 확인 → 커서가 grab으로 바뀌는 것으로 히트 테스트 성공 확인 → `console.log`로 `info.point`·계산된 `deg`가 정상인데 바깥쪽 `angle` 변수만 그대로인 것을 확인 → 원인 특정). 바깥쪽 `setAngle` 정의 바로 뒤에 별칭 `var applyAngleFromScene = setAngle;`을 만들어 끌기 핸들러가 이 별칭을 부르게 고쳤다.

**확인(수정 뒤)**:
- 손전등 위 여러 지점(머리·버튼 옆·목·노즐)을 마우스 다운→이동×2~4→업으로 끌어 각도가 정확히 바뀌는 것을 확인(`t7-multipoint`류 시험, 예: 45°→47/49/50°, 45°→13°). 계산값도 공식과 일치(13°일 때 빛의 세기 225=round(1000·sin13°), 그림자 21.7cm=round(5/tan13°,1)).
- 끄는 동안 슬라이더 값(`#ang-range`)·값 패널(각도·빛의 세기·그림자)·기록 버튼 글자가 모두 실시간으로 같은 값을 보였다(동기화 확인).
- 끌기가 끝난 뒤 빈 배경을 드래그하면 카메라가 정상적으로 회전하고(`v.draggable`이 끄는 동안만 `controls.enabled=false`로 잠갔다가 되돌림), 드래그 직후 각도 값은 변하지 않았다(오브젝트 끌기와 카메라 회전이 서로 안 섞임, `08-after-camera-rotate.png`).
- 끌기로 각도를 바꾼 뒤 기록 버튼을 눌러 정상적으로 기록되는 것, 30°·80° 스냅 버튼으로 필수 두 칸을 채우고 실험하기 게이트가 통과하는 것을 확인.
- 크게 보기(막대) 모드에서도 같은 방식으로 손전등을 찾아(호버 커서로 위치 확인 후) 끌었더니 막대 위 값(`각도45°빛의 세기707…` → `각도43°빛의 세기682…`)이 정확히 갱신됐다(`13-clean-toggle-on-after-drag.png`).
- 끌기는 3D 장면에서만 동작한다(2D 대체 화면은 원래대로 슬라이더만 — 지침·기존 설계와 일치).
- 실험 화면 안내 문구(`.ss-view-tip`)에 "👆 손전등을 끌면 각도가 바뀌어요 · 그 밖은 드래그: 돌려 보기 …"를 추가해 끌 수 있다는 것을 텍스트로 안내했다(spec §3.1의 "정적 화살표나 텍스트로 안내" 원칙, 애니메이션 없이 글자로만 — `prefers-reduced-motion` 분기 불필요).

## 3. "⛶ 전체 화면 보기"(`enlarge()`) 연결

`index.html`의 `sim3d.js` 뒤에 `<script src="./science-sim/experiment.js"></script>`를 추가하고, `app.js`에서 실험 화면을 다 만든 직후 다음을 호출했다.

```js
var enl = S.Experiment.enlarge({
  layout: R.layout, viewBox: R.viewBox, panel: R.panel,
  record: R.record, scenePanel: R.valGrid,
});
```

- 기존에 `panel`·`R.viewBox`(=`.ss-exp-view`)는 있었지만 `layout`(`.ss-exp-layout`)과 값 3칸 카드(`val-grid`)가 지역 변수에 저장돼 있지 않아, 이를 `R.layout`·`R.panel`·`R.valGrid`로 잡아 두도록 살짝 고쳤다(새 카드를 만들지 않고 기존 값 카드를 그대로 재사용).
- `mount()`가 3D↔2D를 바꿀 때(`R.viewBox.classList.toggle("is-2d", …)` 직후) `enl.fit()`을 호출해 크게 보기의 장면 높이를 다시 맞춘다.
- **토글 자리(왼쪽 위, 모형 배지 아래)에 이 앱의 다른 HUD가 있는지 확인**: 이 앱의 "조도 측정 앱(모형)" HUD(`.lux-hud`)는 원래부터 `top:10px; right:10px`(오른쪽 위)라 토글과 안 겹친다 — 옮길 것이 없었다(스크린숏 `02`·`10`·`12`로 확인).

**확인(기록 버튼·측정값이 막대로 옮겨가는지)**:
- 1024×768(가로, 기본은 꺼짐) 상태에서 토글을 눌러 켜니 막대에 값 한 줄(각도·빛의 세기·그림자) + 기록 버튼이 나타나고, `.ss-view3d`가 막대 위에서 끝나며(`has-bar`), 막대 아래쪽이 아래 이동 막대보다 9px 위에서 끝나 안 겹쳤다(`barBottomVsFooterTop: -9.1`, `12-clean-toggle-on.png`).
- 768×1024(세로, 태블릿 세로라 기본 켜짐)에서도 막대가 정상적으로 나타났다(`14-768x1024-portrait.png`).
- 토글을 끄면 값 3칸·기록 버튼이 원래 자리(조작 카드 안)로 정확히 되돌아갔다(같은 엘리먼트 이동 — 복제 아님, 여러 번 반복해도 노드 1개 유지 확인).
- 20개 앱 중 이 앱과 `sci-6-2-1-3`을 대상으로 fix-A 단계에서 이미 `enlarge()` 연결이 스크래치 사본으로 한 차례 시험됐었다(`docs/science/sim-redesign/fix-A-report.md` F9) — 이번 Build는 그 결과를 저장소 코드로 그대로 반영한 것이다.

## 5. 새로 찾은 것 (낮음, 이번에 손댐/문서로만 남김)

1. **좁은 화면에서 손전등 이름표가 토글과 겹침(고침, 완전히는 아님)**: 375px 폭 등에서 손전등이 왼쪽 위에 있을 때 `torchLabel`("🔦 손전등(태양)")이 새로 생긴 토글 버튼과 부분적으로 겹쳤다(`23-phone-scene-zoom.png` 전). review-A2의 N3(`sci-6-2-2-3`·`sci-6-1-2-2`)와 같은 종류인데, 그때는 이 앱에 토글이 없어 빠져 있었다. `torchLabel`의 `narrow` 옵션을 기본값 "grow"(좁은 화면에서 1.4배로 커짐)에서 "keep"(안 커짐)으로만 바꿔 겹치는 범위를 줄였다(`23-phone-scene-zoom.png` 후 — 라벨이 더 커지지 않아 토글 오른쪽으로 더 많이 보임). **완전히 없애려면 3D 좌표→화면 좌표 투영 계산이 필요해 이번 범위를 넘는다고 판단**하고 여기 남긴다 — N3와 같이 "낮음", 필요하면 단계 D에서 한 번에.
2. **812×375에서 크게 보기를 수동으로 켜면 막대가 아래 이동 막대와 약 25px 겹침**(§6과 성격이 다름 — 이건 **기본값이 꺼짐**인 화면에서 학생이 **직접 켰을 때만** 생긴다, `30-812x375-on-forced.png`). spec.md §2.3 다이어그램이 이 크기를 "가장 낮음"으로 표시해 둔 만큼 여유가 가장 적은 조합이다. 공통 틀(`enlarge()`)의 장면·막대 높이 계산이 세로/좁은 화면에서는 vh 기준 고정값(§6 참고)이라 이 극단적인 화면에서는 여유가 부족하다 — 앱 코드로 고칠 수 있는 범위가 아니라 공통 틀 쪽 검토가 필요하면 보고서로 남긴다.

## 6. 공통 틀에서 이미 알려진 채 남아 있던 것(이 앱에서도 재현, 안 고침)

**세로 태블릿(768×1024)에서 크게 보기가 기본으로 켜진 채 막 실험하기에 들어오면, 기록 버튼(막대)이 첫 화면 아래로 살짝(약 45px) 가려진다**(`14-768x1024-portrait.png`에서 막대의 보라색 끝만 살짝 보임). 원인을 좁혀 보니 `enlarge()`의 `applyForOrientation()`(처음 켜질 때 조용히 `set(pref, {silent:true})`만 부름)은 `fit(false)`를 쓰는데, `fit(false)`는 장면으로 스크롤을 맞추는 로직이 없다(`fit(true)`일 때만, 즉 학생이 토글·머리말 접기·창 크기를 바꿀 때만 자동 스크롤). 이건 앱마다 새로 생기는 문제가 아니라 **`experiment.js`/`enlarge()` 공통 코드가 "처음 들어올 때"는 자동 스크롤을 안 하는 특성**이고, `docs/science/sim-redesign/review-A2.md`의 **L1**("크게 보기로 들어올 때 막대가 첫 화면 밖", "안 고침(지침) … 필수 아님 … 단계 B/D 뒤 한 번에")과 같은 문제다. 직접 확인한 결과 다음 중 아무거나 하면 바로 해결된다:
- 학생이 화면을 손가락으로 80px만 내려도 막대가 완전히 드러난다(겹침 −44.7px → −35.3px, `21-portrait-after-scroll80.png`).
- 토글을 껐다 다시 켜면(`fit(true)`가 자동 호출) 막대가 화면 중앙까지 스크롤된다(`22-portrait-after-toggle-roundtrip.png`).

앱 코드(`app.js`)로 고치지 않았다 — `experiment.js`의 `enlarge()` 함수(공통 틀 사본, `science-sim/`)를 고쳐야 하는 문제라 "공통 틀은 고치지 말고 보고서에 적는다" 원칙에 따라 여기 남긴다. 고친다면 `applyForOrientation()`에서 처음 켜질 때도(`silent`일 때도) `scrollIntoViewSafe(viewBox)`를 한 번 부르는 식이 될 것 같다(20개 앱 전부에 영향을 주므로 단계 B 개별 앱에서 하지 말라는 지침과도 맞다).

## 8. 끝까지 진행·시간

체험 모드(비로그인, 로그인 잠금 꺼짐 가정)로 예상하기→(답 입력)→실험하기→(30°·80° 기록)→기록·분석하기(질문 2개 답+확인)→정리하기(결론 제출+궁금한 점)→학습 마치기까지 **자동화로 끝까지 진행해 오류 없이 완료 카드가 뜨는 것**을 확인했다(`26-finished.png`, `doneCardHidden:false`). 이 과정에서 콘솔 오류·예외 0건, 가로챈 Supabase 요청은 모두 `site_settings` 조회(체험 모드 판별)뿐이었다(§9).

**새로고침 후 이어 하기**도 확인했다: 예상하기 답을 적고 실험하기에서 30°만 기록한 채(80°는 아직) 새로고침했더니, 실험하기 단계 그대로·30° 기록(✅)·80° 미기록(⬜)·각도 슬라이더 30°·예상하기 답 문구까지 모두 그대로 복원됐다(`32-before-reload.png`·`33-after-reload.png`).

**실제 학생 시간은 재지 못했다**(자동화 스크립트는 문자열을 바로 넣고 클릭하므로 사람의 읽기·타이핑 시간을 대표하지 않는다). 대신 정성적으로 비교하면: 새 예상 질문(약 40자)이 이전 질문(약 57자)보다 **짧고**, 손전등 끌기는 슬라이더의 **대안 입력**(새 필수 단계 아님)이며, 크게 보기 토글도 **선택**이라 이 앱이 이미 사용자 승인을 받은 시간표(`spec.md` "개정 1": 예상 0:45·실험 1:50·분석 1:10·정리 1:20 = 약 5:05, 7분 기준에 여유)를 늘릴 요인은 없다고 판단한다. 실측은 Review 단계에서 필요하면 확인을 권한다.

## 9. Supabase 차단 기록

- 자기 전용 headless Chrome(포트 9349, 프로필 스크래치 `build-B/sci-6-2-1-4/profile`, 이번에 삭제함), `--use-angle=swiftshader --enable-unsafe-swiftshader --disable-web-security --host-resolver-rules="MAP *.supabase.co 127.0.0.1:9, MAP supabase.co 127.0.0.1:9"`.
- 모든 탭에서 첫 로드 전에 CDP `Fetch.enable(*supabase.co*)`로 가짜 응답만 돌려줬다(`site_settings` GET → `[{"login_required":false}]`, 그 밖의 GET → `[]`, POST/PATCH/PUT → 201, OPTIONS → 204). 실제 Supabase·Gemini 요청은 0건(모든 요청이 위 가짜 응답으로 가로채짐 — 실행마다 1~2건, 전부 `site_settings` 체험 모드 판별용).
- `localStorage.clear()`는 쓰지 않았다 — 이 앱의 `sci621sim4:v1:*` 키만 지워 가며 시험했다(`ssUiPref:` 키는 이번에 만들지 않았다 — 방향별 크게 보기 선택을 기억하는 키인데 시험마다 새 탭·새 프로필 상태에서 확인해 문제 없었다).
- 개발 서버(3000)는 끝까지 살아 있었고 다른 탭·프로세스는 건드리지 않았다.
- **끝나고 자기 Chrome(9349)은 종료했다**(포트 확인 닫힘). 스크래치는 스크린숏(`shots/`, 31장, 14MB)만 남기고 프로필·시험 스크립트·로그를 지웠다(`rm -rf`는 이번에도 거부됐지만, 폴더별로 나눠 지우니 됐다 — `rm -r`은 통과, `rm -rf`만 막힘).
