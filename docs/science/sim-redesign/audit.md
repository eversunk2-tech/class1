## 방법 요약

* 화면: 이미 떠 있던 개발 서버(`http://localhost:3000/class1/apps/<앱>/index.html` — 주소 끝에 `index.html`을 붙여야 `next dev`가 200을 준다. `.../`만 쓰면 404가 난다. 서버는 그대로 두었다)를, 이 점검 전용 headless Chrome(원격 디버깅 포트 9344, 사용자 데이터 폴더 `…/scratchpad/sim-audit/chrome-profile/`)으로 열었다. 실제 Supabase(`unimxzhstovqptcfmjkf.supabase.co`)는 첫 로드부터 `--host-resolver-rules`로 막고, 모든 `*supabase.co*` 요청을 CDP 요청 가로채기(Puppeteer `setRequestInterception`, 내부적으로 CDP Fetch 도메인 사용)로 가짜 응답(`site_settings` GET → `login_required:false`, 다른 GET → `[]`, POST → 201 `[]`, OPTIONS → 204)으로 받았다 — 로그인하지 않았으므로 20개 앱 모두 **체험 모드**로 동작했다. 실제 Gemini 호출은 없음(체험 모드는 애초에 부르지 않는다).
* 3D 장면은 `--use-angle=swiftshader --enable-unsafe-swiftshader`로 WebGL을 켰다. 태블릿 세로(768×1024)·가로(1024×768) 두 뷰포트에서 예상하기 → 실험하기로 들어가 대표 조작(시각·조건 버튼, 각도 슬라이더, ▶ 실행 버튼 등)을 했다. `sci-6-2-1-3`·`-5`는 필수 기록 칸을 전부(12칸·8칸) 채워 분석 단계까지 갔다. 자동화 스크립트(Puppeteer, 이 점검 전용, 프로젝트에는 추가하지 않음)로 각 앱을 두 차례 돌렸는데, 1차 때 실수로 `sci-6-2-1-3`의 "지난 경로 보이기" 토글을 꺼 버려 고스트 자취를 확인하지 못했다 — 이 앱의 `localStorage`(`sci6…` 키만)를 비우고 다시 돌려 바로잡았다(아래 표는 바로잡은 결과).
* 끝난 뒤 Chrome을 껐다(확인함, 남은 프로세스 없음). 스크린숏만 `…/scratchpad/sim-audit/`에 남기고 나머지 임시 파일은 지웠다. `localStorage.clear()`는 쓰지 않았고 그 앱의 `sci6…` 키만 지웠다. 다른 탭·프로세스는 건드리지 않았다. git commit/push 없음.

### `sci-6-2-1-2` — 하루 동안 태양 고도·그림자 길이·기온

**배경(사용자가 이미 지적한 것)**: "태양 그림과 태양빛 선이 맞지 않고, 태양과 지면이 줄로 연결된 것처럼 보인다", "각도기가 너무 크다".

3D 장면(`app.js`)의 좌표를 코드로 따라가 보면:
* 태양(`sunMesh`)은 **원점(0,0,0) 기준** 반지름 `SKY_R = 34`인 하늘 위에 있다 — `sunMesh.position.copy(dir).multiplyScalar(SKY_R)`(**app.js:625**, `dir`는 방위각·고도로 만든 단위 벡터).
* "햇빛"(`ray`, 주황색 얇은 원통, 반지름 0.16)은 **막대기 끝(원점에서 y로 약 11만큼 위) 기준**으로 시작한다 — `var from = new T.Vector3(0, 1 + C.stickCm, 0).addScaledVector(dir, 26)`(**app.js:630**), 끝점은 그림자 끝(`tipW`)이다(**app.js:631** `stretch(ray, from, tipW)`).
* 즉 태양은 "원점에서 34만큼", 햇빛의 위쪽 끝은 "막대기 끝(원점에서 y로 11 떨어진 점)에서 26만큼" — **서로 다른 기준점**에서 같은 방향으로 뻗어 나간 두 값이라 태양 구슬과 햇빛 원통이 실제로 맞닿지 않는다. 게다가 햇빛은 두께가 일정한 가는 원통 하나뿐이라 "빛다발"이 아니라 정말 **막대기와 태양을 잇는 줄**처럼 보인다 — 회색 "실"(`thread`, 막대기 끝→그림자 끝, **app.js:410, 602**)과 색만 다를 뿐 같은 자리에 겹쳐 있어 더 그렇다.
* 스크린숏으로 확인: 15:30(태양이 낮음, 그림자 김) 상태에서 노란 선이 태양 구슬에서 막대기 밑동까지 **팽팽한 실처럼 일직선**으로 이어진다(`sci-6-2-1-2-04-experiment-interacted-portrait.png`, 크롭 `crop-6-2-1-2-device-final.png`). 12:30(태양이 높음)에서도 같은 모양이 짧게 나타난다(`crop-6-2-1-2-device-1230.png`).
* 각도기(`prot`, **app.js:412~456**)는 반지름 `PR = 6`(지름 12)로, 받침판 깊이(9)·자 폭(3.2)·막대기 굵기(반지름 0.4)에 비해 크게 잡혀 있다. 스크린숏에서는 대부분 라벨에 가려 잘 안 보이지만, 노출된 가장자리만 봐도 자 폭을 넘어선다 — 사용자가 말한 "너무 크다"와 일치한다.

**겹침**: "태양 고도 61.7°" 라벨(`lblSolar`, **app.js:612-613**, 위치는 `dev.localToWorld(L+1, 1+PR+3.2, 0)`)과 "그림자 길이 7.9cm" 라벨(`lblShadow`, **app.js:614-615**, 위치는 `L/2+2, 3.2, 6.4`)이 **각도기·그림자 끝 초록 마커 바로 위**에 포개져, 막대 확대 스크린숏(`crop-6-2-1-2-shadowtip-1230.png`)에서 각도기가 거의 안 보인다(왼쪽 위 모서리만 살짝 보임). 값이 바뀔 때마다(그림자 길이가 짧아지거나 길어질 때마다) 라벨 위치도 같이 움직이므로 이 겹침은 시각 대부분에서 나타난다.

### `sci-6-2-1-3` — 계절별 태양의 남중 고도와 낮의 길이

**배경(사용자가 이미 지적한 것)**: "월별 궤적이 계속 남아 헷갈린다."

`spec.md` 개정 1은 "이전 달의 경로를 흐린 선으로 남겨 두어… (선택 토글)"이라고 명시해, 이 동작은 **의도된 설계**다. 문제는 기본값과 라벨이다.
* `var ghostsOn = store.get("ghosts", true) !== false;`(**app.js:125**) — **기본이 켜짐**이고, 끄는 토글("👣 지난 경로: 보임/숨김")은 화면 아래쪽 버튼 한 줄로만 있다.

* **화면으로 확인**: `localStorage`를 비우고(기본값 그대로) 9개월(3~10월 일부, 9~10월 일부)을 기록한 상태에서 "지난 경로: 보임"이 표시되고, 장면에는 색이 다른 곡선 여러 개와 "3월"·"4월"·"9월"·"8월" 등 이름표 여러 개가 한 하늘에 동시에 떠 있다(`sci-6-2-1-3-04-experiment-interacted-portrait.png`). **확대하면**(`crop-6-2-1-3-labels.png`) "9월"·"4월"·"3월" 이름표 상자가 서로 맞닿아 있고 "8월" 상자는 "9월" 상자 뒤에 거의 다 가려지며, 동쪽 방위 글자("동") 위에도 다른 이름표가 겹쳐 있다 — 사용자가 말한 "헷갈림"이 라벨 겹침으로 그대로 나타난다.

### `sci-6-2-1-5` — 계절 변화의 원인(지구본·전등)

이 앱은 실제 3D 지구본이 궤도를 따라 움직이고 자전축이 물리적으로 기울어지는, 조작감이 좋은 편인 앱이다(가·나·다·라 4자리 × 수직/기울임 2조건 = 8칸을 전부 기록해 분석 단계까지 확인함).

`spec.md`가 스스로 적어 둔 주의사항(사용자 확인 대상 절): *"나 위치에서 북반구가 전등 쪽으로 기울어(여름) 그림자가 가장 짧고(0.8cm) 라에서 반대(겨울, 3.5cm)가 되도록 배치를 맞춘다… 그림자 값은 교과서 예시 값을 그대로 표시한다(23.5° 기하 계산값을 쓰지 않음)."* — 코드로 확인하면:
* `function shadowOf(tilt, pos) { return C.shadows[tilt][pos]; }`(**app.js:49-50**) — 그림자 **길이**는 항상 교과서 표의 고정값(가/나/다/라 × 수직/기울임)이다.

## 공통(템플릿) 원인 — 여러 앱에 걸친 구조적 문제

**`scripts/templates/science-sim/sim3d.js`의 `label()` 헬퍼(491-529행)는 카메라를 향한 캔버스 스프라이트를 만들 뿐, 라벨끼리 또는 라벨과 다른 장면 요소 사이의 겹침을 피하는 로직이 전혀 없다.** 값이 바뀌면(그림자 길이·기록한 달 수 등) 라벨 위치도 같이 움직이므로, 특정 조건에서 "라벨이 다른 라벨을 가림"(`sci-6-2-1-3`) 또는 "라벨이 중요한 장면 요소를 가림"(`sci-6-2-1-2`의 각도기)이 반복될 수 있는 근본 원인이다. 이 한 파일만 고치면(예: 최소 이격 로직, 지시선, 또는 겹치는 라벨을 자동으로 옆으로 밀어내는 간단한 규칙) 20개 앱 전부에 적용된다 — Plan 단계에서 "공통 틀 개선" 후보로 검토할 만하다.

**조작감**: 사용자가 원하는 "장면을 직접 끌거나 누르는 느낌"과 비교하면, 대부분의 앱은 재료·조건을 **버튼(칩)으로 고르는** 방식이고, 3D 장면 자체를 직접 드래그하는 것은 "돌려 보기"(카메라 회전)뿐이다. 예외적으로 `sci-6-2-1-2`(시간 바를 직접 끌 수 있음)·`sci-6-2-1-4`(각도 슬라이더)·`sci-6-2-1-5`(위치를 눌러 지구본이 실제로 이동)는 비교적 손맛이 있다. 나머지 다수 앱(재료 칩→▶ 실행 버튼 순서)은 "물체를 직접 만진다"는 느낌보다는 "메뉴에서 고른다"는 느낌에 가깝다.

## 확인하지 못한 것
* **실제 iPad/태블릿 터치**: 이번 점검은 headless Chrome의 마우스 클릭·프로그램으로 만든 슬라이더 값 변경으로 대신했다. 실제 손가락 드래그(3D 회전, 시간 바, 각도 슬라이더)의 감도·오작동 여부는 확인하지 못했다.
* **`sci-6-1-1-1~4`, `sci-6-1-2-1~2`, 여러 2학기 2·3단원 앱의 "실행 결과 화면"**: 재료·조건을 고르는 단계까지는 확인했지만, 그 뒤 "▶ 실행"이나 "측정하기"를 눌러야 나오는 최종 관찰·측정 화면 다수는 자동화 스크립트가 앱마다 다른 다단계 순서(재료 선택→실행→관찰 확인→기록)를 완전히 따라가지 못해 코드 읽기로만 판단했다. 이 앱들의 실행-후 화면에 숨은 겹침·싱크 문제가 더 있을 수 있다.
* **`sci-6-2-1-5`의 그림자 길이-기울기 방향 일치**: 코드상 위험 요인(길이는 고정표, 방향만 계산)은 찾았지만, 측정 장치가 화면에서 매우 작아 "나·기울임(0.8cm)"과 "라·기울임(3.5cm)"을 나란히 놓고 실제로 짧고 길어 보이는지 비교하지 못했다.
* **`sci-6-2-1-4`의 "가로 진입 직후 기록하기 버튼이 하단 막대에 걸침"**(STATUS.md에 이미 기록된 낮은 우선순위 지적): 이번 점검은 항상 세로에서 먼저 조작한 뒤 가로로 바꿨기 때문에 "가로로 처음 들어간 순간"을 재현하지 못했다.
* **소리(버저 등)**: `sci-6-2-3-2`의 버저 소리 크기·`sci-6-2-2-*`의 효과음은 headless 환경이라 실제로 들어보지 못했다(화면 표시만 확인).
* **`sci-6-2-1-2` 완료 토스트 외의 다른 토스트/안내 문구**: 모든 `toast(...)` 호출은 코드로 읽었지만(스포일러 없음 확인), 특정 조합에서만 뜨는 `notice`(2D 전환 등) 일부는 실제로 화면에 띄워보지 못한 경우가 있다.
