## 1. 1학기 1단원 간략화

### 1.1 DB 영향 분석 (결론: 영향 없음 — 코드로 확인)

**주장**: `app_results`(완료 결과)는 순수 추가(insert-only) 테이블이라 질문을 줄여도 이미 저장된 기록은 전혀 바뀌지 않는다. `app_progress`(진행 중 기록)만 저장 키 버전을 올리면 자동으로 초기화된다(허용된 트레이드오프). 관리자 "학생 응답" 화면은 매핑 파일에 **새 변형(variant)**을 추가하면 예전·새 모양을 모두 올바르게 표시한다.

**근거(파일:행)**

1. **`app_results`는 insert-only다.** `scripts/templates/class1-record.js:221-234`:
   ```js
   var res = await state.client
     .from("app_results")
     .insert({ app_id: state.appId, user_id: user.id, ..., details: JSON.parse(detailJson) })
     .select("id")
     .single();
   ```
   update/upsert가 없다 — 완료할 때마다 새 행이 추가될 뿐, 기존 행을 절대 건드리지 않는다. 앱의 `detail` 모양이 바뀌어도 **이미 저장된 행의 `details`는 그대로**다.

2. **`app_progress`(진행 중)는 저장 키(storageKey)가 다르면 자동으로 버려지고 덮어써진다.** `scripts/templates/science-sim/persist.js:784`:
   ```js
   function usable(row) {
     return row && row.state && ... && row.state.prefix === root && ...
   }
   ```
   `root`는 지금 페이지의 `storageKey`다. DB에 저장된 진행 상황의 `state.prefix`(예전 storageKey)가 지금 페이지의 `root`(새 storageKey)와 다르면 `usable()`이 false를 돌려주고, 호출부(`persist.js:892-895`)가 `forceOverwrite = true; row = null;`로 처리한다 — 즉 **예전 버전의 진행 중 기록은 무시되고, 학생이 이어서 진행하면 같은 DB 행(`user_id`+`app_id`로 유일)이 새 모양으로 덮어써진다.** `app_progress`는 `app_id`(앱 폴더 이름, 안 바뀜)로 키가 잡히지 grid `storageKey`로 잡히지 않으므로, 버전을 올리면 "그 앱을 하다가 만" 학생만 처음부터 다시 시작한다. **완료(`app_results`에 이미 들어간) 기록은 이 흐름과 무관**하다(1번 참고).

3. **관리자 "학생 응답" 매핑은 `variants` 배열이 이미 이런 상황을 위해 설계되어 있다.** `src/data/app-responses/types.ts:88-89` 주석: "같은 앱이라도 버전에 따라 detail 모양이 다르다... 위에서부터 match되는 첫 변형을 쓴다." 지금 6개 앱은 모두 `variants: [{ id: "v1", match: () => true, ... }]`(예: `src/data/app-responses/sci-6-1-1-1.ts:39`) 하나뿐이다 — **새 변형을 배열 맨 앞에 추가**하고 기존 `v1`(`match: () => true`)은 그 뒤에 그대로 두면, 새 모양의 완료 기록은 새 변형이 먼저 잡고, 예전 모양은 새 변형의 조건에 안 맞아 자동으로 `v1`(예전)로 떨어진다 — **두 모양을 동시에 정확히 표시**한다(§1.4에 앱별 구체적인 match 조건).

**결론**: 6개 앱 모두 "질문 삭제"만으로는 `app_results`(진행 표시·"학생 응답" 조회)에 어떤 영향도 없다. 유일한 부작용은 **저장 키 버전을 올리면 그 순간 "진행 중"이던 학생만 처음부터 다시 시작**하는 것인데, 이 6개 앱은 STATUS.md에 "학생 사용함"(과거형)으로 기록되어 있어 지금 진행 중인 학생이 있을 가능성은 낮다(단, 확인은 못 했다 — §8 열린 질문). **이 계획에서 "영향 있어 수정하지 않는" 앱은 없다** — 6개 모두 간략화를 진행한다.

### 1.2 중요: 기존 CLAUDE.md 규칙과의 충돌

`CLAUDE.md`와 `docs/STATUS.md`에는 "1학기 1단원 전체와 2단원 탐구 1·2·6은 **문항·내용을 이전 기준 그대로 둔다**(수업에서 이미 사용했거나 사용하지 않음)"(2026-09-22 결정)이 적혀 있다. 이번 사용자 요청(2026-09-25)은 **1학기 1단원에 한해 이 결정을 뒤집는 것**이다(2단원 탐구 1·2는 여전히 예외로 남는다 — 사용 안 함, 문항 그대로). §0.3의 단계 C가 끝나고 사용자가 최종 승인하면, `CLAUDE.md`의 해당 문장과 `docs/STATUS.md`의 표를 갱신해 이 결정을 기록한다(Claude가 마무리 단계에서 처리).

### 1.3 공통 규칙

- 목표 문항 수(2026-09-22 기준): 예상하기 1개, 분석(퀴즈) 1~2개, 정리하기 1개(발전 질문 없음), 궁금한 점 1개(필수, 이미 충족). **조사(guide) 앱은 도입 질문 1개·정리 질문 1개**가 같은 기준.
- **측정·분류·기록 활동(`records`, `classify`/`Sorter.renderRounds`, `myCriterion` 같은 앱 전용 조작형 활동, `worksheet`, `share`)은 건드리지 않는다.** 이유: (a) 사용자 지시가 "질문 수·길이"이지 조작 활동이 아니다, (b) 이런 활동은 탭·드래그 기반이라 서술형 질문만큼 시간을 잡아먹지 않는다, (c) 일부는 명시적 학습 목표(예: `sci-6-1-1-1`의 `myCriterion`은 "분류 기준을 세워 분류"라는 학습목표 2를 담당 — `data/lesson-config.js:139` 주석)를 담당해 제거하면 내용 변경이 된다. 단 `sci-6-1-1-6`의 `fill`(빈칸 채우기)과 `why`(서술형)는 사실상 "분석 문항"의 변형이라 아래에서 정리 대상에 포함했다(§1.4).
- **남긴 질문의 문구는 원칙적으로 바꾸지 않는다.** 다만 "길이만 줄이는" 것도 허용 범위이므로, Build 단계에서 과하게 긴 질문은 뜻을 안 바꾸는 선에서 다듬을 수 있다(필수 아님).
- **힌트(hints)는 남긴 질문에 맞는 것만 남긴다**(대개 3개 → 1~2개). 힌트 문구 자체는 바꾸지 않고 고르기만 한다.
- **`app.js`의 `buildDetail()`도 함께 고친다** — config에서 문항을 빼는 것만으로는 부족하다. 예를 들어 `extension` 객체를 만드는 코드가 남아 있으면 `{q1: undefined, q2: undefined}`처럼 빈 값이 들어간 채 저장되거나, 아예 에러가 날 수 있다. **뺀 문항에 대응하는 `detail`의 키 자체가 생기지 않도록** `buildDetail()`을 고쳐야 새 변형의 `match()`(빠진 키의 "없음"을 확인하는 방식)가 정확히 동작한다.
- 이번 간략화는 `detail.qa`(§0의 "질문-답 표준 목록")를 추가하지 않는다 — 범위 밖(기존 결정, `docs/admin/responses-spec.md` §11 Q1과 일관: 구 기준 앱 9개에 `qa()` 소급 안 함). 매핑 파일의 `variants`만으로 새·구 모양을 모두 표시한다.

## 2. 공통 틀: 전체 폭 실험 화면

### 2.1 지금 구조

`experiment.js`가 실험하기 화면 DOM을 만든다(`create()` 함수, `scripts/templates/science-sim/experiment.js:257-353`): 3D/2D 장면 박스(`R.viewBox`, class `ss-exp-view`)와 보기 도구 버튼이 `viewCol`로 묶이고, 조건 고르기 카드·실행 카드·관찰/기록 카드·미니 표가 `panel`로 묶인 뒤, 맨 끝에 `o.root.appendChild(el("div", { class: "ss-exp-layout" }, [viewCol, panel]))`(`experiment.js:353`)로 두 블록을 나란히 넣는다. 배치는 CSS 한 곳(`style-common.css:342-348`)이 정한다:

```css
.ss-exp-layout { display: grid; grid-template-columns: minmax(0, 1.35fr) minmax(320px, 1fr); gap: 16px; align-items: start; }
.ss-exp-view-col { position: sticky; top: calc(var(--ss-header-h) + 8px); }
@media (max-width: 900px), (orientation: portrait) {
  .ss-exp-layout { grid-template-columns: 1fr; }
  .ss-exp-view-col { position: static; }
}
```

즉 **세로 화면·900px 이하에서는 이미 위아래로 쌓인다.** 사용자가 "좌우로 나뉜다"고 느낀 화면은 주로 **가로 태블릿(1024×768, 900px보다 넓음)**과 큰 화면일 것이다 — 이 폭에서는 지금도 장면(1.35fr)과 조작 패널(1fr, 최소 320px)이 나란히 있다. 그리고 세로 화면이라도 지금 장면 높이는 `min(44vh, 520px)`(`style-common.css:355`)로 작아, "전체 폭을 꽉 채워 주인공처럼 보이는" 느낌은 약하다.

`sci-6-2-1-2`는 이 한계를 이미 앱 코드로 우회한 사례가 있다: 값 패널(`vp`)을 `matchMedia`로 감시해 가로 넓은 화면(`min-width:901px and orientation:landscape`)이면 `.ss-exp-panel`(조작 패널 칼럼) 맨 위에, 아니면 장면 바로 아래에 직접 `insertBefore`로 옮긴다(`public/apps/sci-6-2-1-2/app.js:959-970`). 이런 **앱마다 다시 만든 반응형 배치 코드**를 공통 틀이 정식으로 지원하는 것이 이번 개편의 목적이다.

### 2.2 새 레이아웃 (옵트인 `SciSim.Experiment.create({ fullScene: true, scenePanel: node })`)

넘기지 않으면(기본값) **지금과 완전히 동일**(픽셀 단위로 안 바뀜) — 20개 앱을 한꺼번에 공통 틀 사본 교체해도 안전하다. `fullScene: true`를 준 앱만 새 배치를 쓴다.

**바뀌는 것**
1. `.ss-exp-layout.is-full`은 화면 폭과 무관하게 **항상 1열**(grid-template-columns: 1fr). `.ss-exp-view-col`은 sticky 해제(항상 그대로 흐름).
2. 장면 박스(`.ss-exp-view`) 안, 아래쪽에 반투명 오버레이 막대(가칭 `.ss-exp-overlay`)를 새로 만든다. 이 막대에는:
   - **실행("▶ …") 버튼** — 지금 조작 패널 카드에 있던 `R.run`을 이 막대로 옮긴다(중복 렌더링 대신 이동).
   - (선택) `scenePanel` 옵션으로 앱이 넘긴 노드(예: `sci-6-2-1-2`의 값 패널 `vp`) — 공통 틀이 이 자리를 정식 제공하므로 앱은 더 이상 `matchMedia` 코드를 직접 짤 필요가 없다.
   - **조건 고르기 버튼(색깔·용액 등 여러 개 보기가 있는 카드)은 오버레이에 넣지 않는다** — 촘촘한 버튼 격자를 반투명 막대 위에 올리면 터치 인식률·가독성이 떨어지고 스크린리더 순서도 꼬이기 쉽다. **장면 바로 아래**(기존 `panel` 위치, 이제는 전체 폭)에 그대로 둔다. 이는 plan-instructions의 "겹쳐 놓을 수 있으면 넣고, 아니면 장면 바로 아래" 원칙 중 "아니면"에 해당하는 선택이다 — 이유는 §8에서 대안(오버레이에 보기까지 넣는 더 야심찬 버전)과 함께 정리했다.
3. **떠 있는 기록 버튼**: 관찰 카드의 "기록하기" 버튼(`R.record`)이 켜져 있는데 화면 밖으로 스크롤되면, 아래 이동 막대(`.ss-footer-nav`) 바로 위에 같은 라벨의 작은 알약 버튼을 띄운다. 누르면 실제 `R.record`와 같은 동작(클릭 이벤트 재사용, 별도 스크롤 없이 바로 기록). 지금도 `revealRecord()`(`experiment.js:744-753`)가 기록 버튼이 가려지면 자동 스크롤하는데, 전체 폭 레이아웃에서는 장면이 커진 만큼 스크롤 거리가 늘 수 있어 이 보완이 필요하다.
4. **접는 기록 표**: 지금도 `.ss-mini-box`가 `<details>`라 이미 접고 펼 수 있다(`experiment.js:343-349`). 전체 폭에서는 이 표가 조작 패널과 같은 전체 폭을 쓰므로 가로 스크롤이 줄어든다(예: `sci-6-2-3-3`의 7칸 표).
5. 장면 높이는 방향·화면 크기별로 공통 틀이 정한다(아래 2.3). 앱 `style.css`가 `.ss-exp-view` 높이를 직접 재정의하던 관행은 **새 레이아웃에서는 대부분 지운다**(공통 틀의 새 규칙을 따름). 앱이 정말 특별한 높이가 필요하면 `--ss-scene-h` 같은 CSS 변수 오버라이드 한 줄만 허용(선택). 조사 결과 20개 sim 앱 중 **`.ss-exp-layout`(좌우 분할)이나 `.ss-exp-panel` 자체를 건드린 앱은 없다** — 모두 `.ss-exp-view`의 "높이"만 화면 크기별로 재정의했다(4~6개는 2단계, `sci-6-2-2-3`은 6개 규칙으로 가장 복잡 — §5.1). 즉 전체 폭으로 옮기는 작업은 "분할 CSS와의 충돌"보다는 "각 앱이 좌우 분할 비율에 맞춰 튜닝해 둔 높이 값을 전체 폭 기준으로 다시 튜닝하는" 작업에 가깝다 — 단순 삭제가 아니라 **앱마다 재확인이 필요**하다는 뜻으로 Build 시간을 잡는다.
6. **작은 공통 틀 추가(선택, §8)**: `sim3d.js`에 `v.draggable(obj, onDrag)` 도우미를 추가하는 것을 권장한다. 지금 `sim3d.js`는 탭(레이캐스트 1번, `pickable`/`onPick`)과 카메라 드래그(OrbitControls)만 지원하고 **물체를 끄는 제스처는 없다**(`sim3d.js:307-341`). §4의 `sci-6-2-1-2`(태양/그림자)·`-4`(손전등)·`-5`(지구본) 3곳에서 "직접 끌기" 아이디어를 냈으므로, 앱마다 레이캐스트를 새로 짜는 대신 공통 틀에 한 번 만드는 편이 안전하다(포인터다운→포인터무브→포인터업 시퀀스에서 평면 교차점을 계산해 콜백으로 넘기는 정도의 작은 함수 — 기존 `pickable`과 마찬가지로 **완전히 선택 사항**이라 안 쓰는 17개 앱에는 영향이 없다).

### 2.4 3D 카메라·성능·접근성

- **카메라는 코드 변경 없이 자동 대응한다.** `Sim3D.create()`의 `computeFit()`(`sim3d.js:131-142`)과 `resize()`(`sim3d.js:151-166`)가 `ResizeObserver`로 컨테이너의 실제 `clientWidth/clientHeight`를 읽어 카메라 거리를 다시 계산한다 — 장면 박스가 넓어지거나 아스펙트비가 바뀌어도 `frame.width/depth`만 앱마다 맞으면 저절로 맞춰진다. Review에서 극단적으로 넓고 낮은 가로 화면(1024×768, 장면 높이 40vh)에서 물체가 너무 작아 보이지 않는지 앱별로 눈으로 확인한다.
- **성능**: 장면 박스 면적이 커지면(예: 기존 좁은 칼럼 약 340×520 → 전체 폭 약 1000×450) GPU가 그릴 픽셀 수가 늘어난다. `renderer.setPixelRatio(Math.min(devicePixelRatio, 2))`(`sim3d.js:100`)로 이미 상한이 있고 장면들은 저폴리곤(README 표현)이라 위험은 낮다고 보지만, **실제 태블릿 확인은 못 했다**(`docs/STATUS.md` "확인하지 못한 것"에도 있음) — Phase A Review에서 실기기(또는 최소 크롬 성능 패널)로 드래그 회전이 버벅이지 않는지 확인을 새 항목으로 추가한다.
- **접근성**: 오버레이 버튼도 44px 이상 터치 영역(`--ss-btn` 최소 48px 이미 충족), 포커스 링(`:focus-visible`) 그대로 적용. **오버레이 안 요소는 시각적 위치와 무관하게 DOM 순서도 논리적으로**(보기 도구 → 오버레이(실행·값) → 조건 카드 → 관찰 카드) 둬서 스크린리더·키보드 탭 순서가 화면에 보이는 순서와 어긋나지 않게 한다. `prefers-reduced-motion`이면 오버레이는 애니메이션 없이 항상 고정 표시(등장 트랜지션을 만들지 않는 것을 권장 — 애초에 안 만드는 게 가장 안전).

## 3. 직접 조작 원칙과 답 알려 주기 금지 원칙

### 3.1 직접 조작 원칙 (공통)

1. **버튼 선택은 항상 남긴다.** 3D 조작은 버튼 선택의 "또 다른 방법"이지 대체가 아니다 — 스크린리더·마우스만 쓰는 기기·드래그가 서툰 학생 모두 버튼으로 여전히 할 수 있어야 한다. `sim3d.js`는 이미 이 패턴을 지원한다: 물체를 `v.pickable(obj, value)`로 등록하면 탭할 때 `ctx.onPick(value)`가 불리고, `experiment.js`의 `ctx.onPick`(`experiment.js:898-911`)은 이미 있는 `pick(fid, oid)`/`select(sel)`를 그대로 호출한다 — **즉 탭 조작을 추가해도 저장되는 값·구조는 버튼 클릭과 완전히 같다**(DB·응답 매핑 영향 없음).
2. **조작 단계를 늘리지 않는다.** 직접 조작은 기존 "고르기 → 실행" 흐름의 고르기 부분을 대신할 뿐, 새로운 필수 동작을 만들지 않는다.
3. **측정 도구를 대거나 누르는 손짓 애니메이션은 1초 안쪽으로.** 시간 예산(7분)을 지키기 위해 연출은 짧게, 결과는 바로 보여준다(`sci-6-1-2-3`의 "빨리 감기(모형)" 관행과 동일).
4. **드래그 가능한 물체는 힌트를 준다**(살짝 흔들리는 아이콘 등 — `prefers-reduced-motion`이면 정적 화살표나 "👆 끌어 보세요" 텍스트로 대체), 히트박스 44px 이상.
5. 이 원칙은 §2의 전체 폭 레이아웃과 별개로도 적용할 수 있다(레이아웃을 안 바꾼 앱도 조작 아이디어만 먼저 넣을 수 있음) — 단 이번 단계 나누기(§0.3)에서는 D 단계에서 같이 넣는 것으로 묶었다.

### 3.2 답 알려 주기 금지 원칙 (공통, 명문화)

- **실험하기 단계·기록하는 순간**(토스트, 관찰 카드 안내 문구, 미니 표의 `aria-label`, 이름표)에는 **결론·관계·인과 표현을 쓰지 않는다.** 금지 표현 예시: "~할수록 ~해요", "그래서 ~이다", "~이기 때문에"(원인·결과를 단정하는 문장), 정답 보기와 같은 문구를 미리 노출. **허용**: 측정값·관찰 사실만 말하는 문장("기록했어요: 12:30 · 51.7°"), 조작 방법 안내("눈금을 맞춰 보세요").
- 분석·정리하기 단계의 정답/오답 피드백, 정리하기 모범 답안 비교는 **원래 허용**(공통 틀 규칙, 학생이 스스로 고르거나 쓴 뒤에 나오는 것이므로 "알려주기"가 아니라 "맞춰보기"). 이 원칙은 **그 전 단계**에만 적용된다.
- 시행 방법: 코드 강제 메커니즘은 만들지 않는다(문구는 각 앱 `lesson-config.js`/`app.js`에 흩어져 있어 일반적 코드 규칙으로 막기 어렵다). 대신 **Review 체크리스트 항목**으로 추가(§7)하고, audit.md가 찾은 기존 사례부터 고친다.

### 4.1 sci-6-2-1-2 (하루 동안 태양 고도·그림자·기온) — 가장 깊은 재설계

**실제로 찾은 싱크 버그(코드로 확인, 추정이 아님)**: `app.js:625`에서 태양 구체 위치는 `sunMesh.position.copy(dir).multiplyScalar(SKY_R)`(`SKY_R = 34`, `app.js:313`)로 두는데, 빛줄기(ray)의 먼 쪽 끝은 `app.js:630` `var from = new T.Vector3(0, 1 + C.stickCm, 0).addScaledVector(dir, 26)`로 **다른 상수(26)**를 쓴다. 막대기 끝이 원점 근처(`stickCm=10`)이므로 빛줄기는 원점에서 약 26만큼만 뻗는데, 태양은 34만큼 떨어져 있다 — **빛줄기 끝과 태양 구슬 사이에 항상 약 8(하늘 반지름의 약 1/4)만큼 빈 틈이 생긴다.** 얇고 반투명한(`opacity:0.55`) 원통이 태양에 닿지 못한 채 허공에 떠 있는 것처럼 보여 "태양과 안 맞는다"는 인상을 준다. (그림자 자체의 방향·길이 공식은 직접 검증한 결과 물리적으로 옳다 — `dev.rotation.y = Math.atan2(Math.cos(a), Math.sin(a))`가 태양 방향 `dir`과 대수적으로 정확히 반대 방향을 가리킴을 확인했다. 문제는 빛줄기 시각화 하나였다.)

**고치는 방향**
1. **싱크**: 빛줄기의 "태양 쪽 끝"을 `dir.clone().multiplyScalar(SKY_R)`(태양 구체와 같은 계산)로 바꾼다 — 상수 26을 없애고 `sunMesh.position`과 같은 값을 쓰게 해서 **두 그림이 한 벡터에서 나오게** 한다(싱크 보장 원칙). "막대기 쪽 끝"도 `dev.localToWorld(...)`로 통일(현재는 회전축 위 점이라 우연히 맞았을 뿐 — 앞으로 장면이 바뀌면 다시 어긋날 수 있으니 명시적으로 고친다).
2. **각도기 크기**: 지금 반지름 `PR = 6`(`app.js:413`)은 10 cm 막대·32×9 받침판 규모에서 과도하게 크다(막대 키의 60%). **작은 호(arc) 표시**로 바꾸는 것을 권장(plan-instructions §4의 "각도 표시는 작은 호" 원칙과 일치) — 지금도 각(`arc`, 빨간 링)이 이미 있으므로(`app.js:458-460`), 반원 각도기 전체를 없애고 이 호와 "○○.○°" 캔버스 라벨만 남기면 시각적으로 훨씬 가벼워진다.
3. **글자 겹침**: 3D 안에 떠 있는 값 라벨(`lblSolar`/`lblShadow`/`lblTemp`, `app.js:464-467, 610-617`)은 **DOM 값 패널(`vp`, `app.js:931-946`)과 완전히 같은 정보를 중복 표시**한다. DOM 패널은 이미 아이콘+글자로 잘 만들어져 있고 스크롤·화면 크기에 안전한 반면, 3D 라벨은 그림자 길이·각도기 반지름에 따라 위치가 계속 바뀌는 스프라이트라 자·각도기 눈금과 겹치기 쉽다(정확히 "글자가 측정값을 가린다"는 지적과 일치). **3D 값 라벨 3개(`lblSolar`/`lblShadow`/`lblTemp`)를 지우고 DOM 값 패널만 남긴다.** 3D에는 고정된 이름표(동서남북, "막대기 10 cm", "자(cm)", "태양")만 남긴다 — 이런 이름표는 값이 안 바뀌므로 겹침 위험이 훨씬 작다.
4. **장면을 더 친근하게(사용자 제안)**: "교과서 도구와 똑같을 필요 없다"는 지시에 따라, 추상적인 측정판(자+각도기+실)을 **나무 한 그루(그림자 관찰 대상)**로 바꾸는 것을 1차 권장안으로 제시한다(§8에서 "사람" 대안과 함께 확정). 물리량은 그대로: 막대 대신 나무 기둥의 높이(10 cm 상당의 모형 나무), 그림자 길이·방향은 지금과 같은 공식(`10/tan(고도)`), 태양 고도는 "나무 꼭대기~그림자 끝을 잇는 선이 지면과 이루는 각"으로 여전히 정확하다 — 다만 **각도기/실 UI는 없애고**, "나무 그림자 길이"와 "나무 끝-그림자 끝 선"만 은은하게 표시한 뒤 **값은 DOM 패널로만** 보여준다(정확한 측정 절차 재현보다 "이렇게 재는구나"를 보여주는 것으로 충분 — 이미 앞 차시(탐구 1, 앱 없음)에서 측정기 자체는 배웠다). 빛줄기는 얇은 원통 대신 **위가 넓고 아래로 갈수록 옅어지는 부드러운 빛기둥**(태양~나무~그림자를 느슨하게 감싸는 형태)으로 바꿔, "실처럼 팽팽한 선"이 아니라 "빛이 비친다"는 인상을 준다(현재 지적된 "줄로 이어진 느낌"의 근본 원인이 재질에도 있다고 판단).
5. **직접 조작**: §3.3에서 제안한 대로 시간 바와 장면을 양방향으로 잇는다(태양/그림자를 직접 끌면 시간 바도 따라 움직임) — MVP로는 생략 가능(§8).

### 4.2 sci-6-2-1-3 (월별 태양 고도·낮의 길이)

**실제로 찾은 문제**: "지난 경로"(ghost) 표시가 **그동안 기록한 모든 달**을 동시에 보여준다. `app.js:338` `return ghostsOn ? recordedMonths() : []` — 기본값 `ghostsOn = true`(`app.js:125`)라 학생이 12개월을 채워갈수록 화면에 남는 경로가 최대 11개까지 쌓인다. 지금은 이걸 껐다 켰다 하는 토글(`app.js:184, 326-327, 415-416`)이 있지만 "전부 보이거나 전부 안 보이거나"뿐이다.

**고치는 방향(사용자 요청 그대로)**
1. **기본값을 "선택한 달만"로 바꾼다** — `ghostList()`가 기본적으로 `[]`를 돌려주게(지금의 `recordedMonths()` 대신). 이렇게 하면 매번 딱 1개의 굵은 경로(지금 달)만 보인다.
2. **"봄·가을·여름·겨울 대표 궤적 3개 비교" 옵션을 새로 만든다.** 대표 3개는 지도서 값(`public/apps/sci-6-2-1-3/spec.md`의 "개정 1" 절, 이 앱 자신의 12개월 표) 기준으로 **3월(봄, 대표) — 9월은 3월과 거의 같아 따로 안 그린다(52.5° vs 52.6°, 낮의 길이도 12:10 vs 12:12로 사실상 같다) · 6월(여름, 최댓값 75.5°) · 12월(겨울, 최솟값 29.0°)**. 이 3개는 학생이 아직 기록하지 않은 달이라도 표시할 수 있어야 한다(참고용 비교이지 "내 기록"이 아니므로 — `pathSamples(month, ...)`는 천문 계산 기반이라 기록 여부와 무관하게 그릴 수 있다, `app.js:572`). 라벨은 "봄·가을(3월경) / 여름(6월경) / 겨울(12월경)"처럼 **두 계절이 한 선임을 명시**해 오해를 막는다(§8에서 문구 확정).
3. 기존 토글 버튼(`btnGhost`, "👣 지난 경로: 보임/숨김")을 **2~3단 전환**(이번 달만 / 대표 3개 비교, 필요하면 + 지금까지 기록한 전부)으로 바꾼다. 저장 키는 `store.get("ghosts", true)`(불린)를 그대로 재해석하면 예전 저장값과 충돌할 수 있으므로 **새 키(`pathMode: "current" | "compare3" | "all"`)**를 쓰고 `ghosts` 키는 그냥 버려둔다(§6에서 상세 — storageKey 버전은 안 올림, 지역 UI 설정 키 하나가 안 쓰이게 될 뿐이라 무해).
4. 글자 겹침(`남중 고도 ○○.○°` 라벨이 지난 경로 이름표에 가리지 않도록 `depthTest:false`+`renderOrder:30`을 이미 쓰고 있다 — `app.js:606-607`)은 기본이 "선택한 달만"으로 바뀌면 자연히 크게 줄어든다.

### 4.3 sci-6-2-1-4 (각도별 빛의 세기·그림자)

이 앱은 이미 **싱크가 잘 설계되어 있다** — `setAngle(deg)` 한 함수(`app.js:722-786`) 안에서 손전등 위치·회전, 빛줄기 지오메트리, 그림자 길이, 각도 호, 라벨 위치를 **모두 같은 `c=cos, s=sin`에서** 계산한다(단일 상태값 원칙의 좋은 예 — §2·§4.1과 대조해 Build 단계에 "이 패턴을 따르라"는 예시로 제시한다). 다만:

- **라벨이 화면 크기·각도에 따라 수동으로 자리를 옮기는 임시방편이 많다.** 예: `torchLabel`의 위치는 `sg = deg < 50 ? 1 : -1`처럼 손전등 이름표가 "다른 화면 요소와 안 겹치도록" 각도 구간별로 부호를 반전시켜 수동 배치한다(`app.js:780-784`). 좁은 화면(<480px)에서는 `fitLabels()`가 라벨 크기·위치를 또 한 번 바꾼다(`app.js:700-718`, `narrowPos` 속성). 이런 **기하 상대 오프셋 임시방편** 대신, plan-instructions가 제시한 "이름표는 장면 가장자리 고정 칸" 원칙(§4.6)을 적용해 상당수를 DOM 오버레이/값 패널로 옮기는 것을 권장한다.
- 거리 표시("20.0 cm (늘 같음)")·각도 숫자 텍스처는 유지(값이 바뀔 때만 다시 그리는 이미 효율적인 구조, `drawAngleText()` `app.js:678-697`).
- 조작: 이미 슬라이더가 있어 직접 조작적이나, 손전등 자체를 끄는 상호작용을 추가하면 더 좋다(§3.3) — `torch` 그룹이 이미 있으므로 `v.pickable(torch, ...)` + 드래그 각도 계산만 추가하면 된다(각도 계산 공식은 `setAngle`이 이미 갖고 있다).

### 4.4 sci-6-2-1-5 (자전축 기울기·위치별 그림자)

이 앱도 **월별 재설계보다 견고한 패턴**을 쓴다 — `drawShadow()`(`app.js:791-804`)가 손전등(`lampPos`)과 지구본(`place.position`)의 실제 월드 좌표·회전을 직접 읽어 그림자 방향을 `atan2`로 유도한다(가상의 az/alt 재계산 없이, 실제 3D 객체 상태에서 직결) — 이 또한 좋은 예로 Build에 제시한다. `updateHud()`(`app.js:812-814`)로 DOM HUD가 이미 있어 값 중복 표시 위험도 적다.

- 확인·정리할 점: 자전축 이름표·"우리나라" 이름표(`app.js:729, 762`)가 지구본이 자전(`spinG.rotation.y`)할 때도 같이 도는지, 위치(가~라)가 바뀔 때 겹치는 곳은 없는지 — audit.md 결과와 함께 최종 확인.
- 조작: 위치(가~라) 버튼 대신 지구본을 궤도 위로 끄는 동작 추가(§3.3), 자전축 기울기는 이미 "수직/기울임" 두 값뿐이라 버튼으로 충분(드래그로 임의 각도를 주는 건 실험관찰 조건(2가지)을 벗어나므로 안 함).

## 7. 검증 계획

### 7.1 화면 크기별 확인 (§2 레이아웃을 켠 모든 앱)
세로 태블릿 768×1024·가로 1024×768·1180×820·휴대폰 375×812·812×375, 다크모드, `?no3d=1`(2D 대체), 3D↔2D 반복 전환(WebGL 컨텍스트 안 쌓이는지), 오버레이 버튼이 아래 이동 막대(`.ss-footer-nav`)나 관찰 카드와 안 겹치는지, 떠 있는 기록 버튼이 실제 기록 버튼과 항상 같은 상태(활성/비활성)를 보이는지.

### 7.2 과학적 정확성(§4 재설계 앱 별도 항목)
- `sci-6-2-1-2`: 빛줄기가 실제로 태양 구체(`sunMesh`)에 닿는지(좌표 비교 또는 스크린숏), 그림자 방향·길이가 태양 위치와 항상 일치하는지(여러 시각에서 확인), 각도기(또는 대체 호) 각도가 `st.solar`와 일치하는지.
- `sci-6-2-1-3`: "이번 달만" 기본값 확인, 3개 대표 비교가 정확히 3월(또는 3·9월 병기)·6월·12월 값을 쓰는지, 12칸 필수 기록이 그대로인지.
- `sci-6-2-1-4`·`-5`: 라벨 재배치 뒤에도 겹침이 실제로 줄었는지(여러 각도/위치에서 스크린숏), 값 패널 숫자와 3D 상태가 일치하는지.
- 공통: "모형" 표시 유지, 지도서 문구("지도서") 미노출, 스포일러 없음(기존 spec.md 체크리스트 재사용).

### 7.3 규칙 준수
예상·정리 질문 개수(§1은 새 개수, §4는 기존 유지), 힌트가 답을 말하지 않음, 분석 보기 고르기 1~2개, **기록 문구가 결론·관계를 먼저 말하지 않음**(§3.2 체크리스트 — 토스트·관찰 안내·이름표 문구를 모두 읽고 금지 표현이 없는지), 마치기 조건("학습 마치기"를 눌러야 제출) 그대로.

### 7.4 시간(7분) 확인
- §1의 6개 앱: 간략화 후 실제로 진행해 시간을 재고, §1.5의 추정과 비교해 `docs/STATUS.md`에 기록한다.

### 7.5 DB·응답 매핑 검증 (§1 앱 전용)
- 코드 확인(변형 순서: 새 변형이 배열 맨 앞, 기존 `match: () => true`가 그 뒤)을 Build·Review 양쪽이 다시 읽어 확인.
- **가짜 완료 기록 2개**(예전 모양 1개, 새 모양 1개 — 스크립트나 관리자 화면에서 직접 만들 수 없으면 코드로 `getResponseSchema(appId).variants`를 순회하며 각 `match()`에 두 `Detail` 객체를 넣어 어떤 변형이 잡히는지 확인하는 작은 확인 스크립트)로 "학생 응답" 화면(또는 매핑 로직)이 올바른 변형을 골라 보여주는지 확인.
