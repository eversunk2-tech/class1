## 4. 사용자가 할 일

1. **학생 기기에서 새로고침(캐시 비우기)이 필요하다.**
   GitHub Pages는 `index.html`에 `cache-control: max-age=600`을 준다. 17:27 배포 직전에 앱을 열어 둔
   기기는 **옛 `index.html`(답 검사 스크립트 줄이 없는 것)을 최대 10분 더 쓴다.** 그 상태에서는 지금도
   `ㅇㅇㅇㅇㅇ…`이 그냥 통과한다.
   - iPad Safari: 앱 화면을 **완전히 닫았다가 다시 열기**(탭 닫기 → 다시 열기). 그래도 안 되면
     설정 › Safari › **방문 기록 및 웹사이트 데이터 지우기**.
   - 배포 후 10분이 지나면 저절로 새 파일을 받는다.
2. **수업에 쓰기 전 1분 점검**: 앱을 열어 예상하기에 `ㅇㅇㅇㅇㅇㅇㅇㅇㅇㅇ`을 적고 '다음 단계'를 눌러
   🚫 카드가 뜨는지 본다. 뜨면 새 판을 받은 것이다.
3. **다른 세션의 작업 트리 변경**(§2 ⚠️)은 아직 커밋·push 전이다. 그 변경을 커밋·배포할지는 사용자가 판단한다.
   (이 보고서 작업에서는 git 명령을 쓰지 않았다.)

## 5. 확인하지 못한 것

* 학생이 실제로 언제 앱을 열었는지는 알 수 없다. 12:37~17:27 사이였다는 것은 **증상과 배포 기록이
  일치한다**는 정황 근거이고, 서버 로그로 확인한 것은 아니다.
* 실제 iPad에서의 캐시 동작은 확인하지 못했다(헤드리스 Chrome으로만 확인).
* 학생의 그 앱 기록에 `answerCheck.teacherOverride`(같은 질문에서 3번 막힌 뒤 "🙋 선생님과 확인했어요"를
  누른 표시)가 남아 있으면 그 질문은 설계상 늘 통과한다. 실 DB를 읽지 않았으므로 이 가능성은 배제하지 못했다.
  다만 그 경로를 지나려면 🚫 카드를 **세 번** 봤어야 하므로, "아무 안내 없이 넘어갔다"는 보고와는 맞지 않는다.
