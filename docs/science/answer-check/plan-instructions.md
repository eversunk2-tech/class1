# Plan 서브에이전트 지침: 학생 답 되짚어 주기(1안 규칙 + 2안 Gemini) — 2026-09-23 사용자 승인

## 배경·요구
지금은 학생이 예상하기·정리하기(서술형)에 아무렇게나 적어도 그대로 넘어가고 칭찬만 나온다. 사용자 요청:
* **말이 안 되는 답·틀린 답이면 "다시 생각해서 써 보자"는 안내가 나오게** 한다.
* **1안(앱 안 규칙 검사)을 기본**으로 모든 과학 차시 앱에 넣는다.
* **2안(Gemini API)도 함께 만들어**, 필요할 때 호출해 더 똑똑한 피드백을 준다. 실패·지연·한도 초과면 1안으로 자동 전환.
* Gemini 피드백은 **초등 6학년 수준의 쉽고 짧은 말**(두 문장 이내, 어려운 용어 금지, 답을 알려 주지 않기).

## 반드시 지킬 것
* **절대 막지 않는다**: 되짚어 주기는 한 번 권유일 뿐, 학생이 그대로 제출하면 다음 단계로 간다(판정이 틀릴 수 있음). 모범 답안 비교는 지금 흐름 그대로.
* **7분 기준**을 해치지 않는다(되짚기 1회, 대기 시간 짧게, Gemini 응답은 최대 몇 초 후 포기).
* **API 키는 저장소·브라우저에 절대 없다.** Supabase Edge Function 안에서만 `Deno.env.get(...)`으로 읽는다. 함수는 Verify JWT를 켜서 로그인 학생만 부를 수 있게 하고, 호출 빈도·글자 수를 제한한다.
* **개인정보 최소화**: Gemini에 보내는 것은 앱 이름·질문 번호·학생이 쓴 답뿐. 이름·학번·이메일·user id 금지. 앱 화면에 "적은 내용을 검사에 보낸다"는 안내를 넣을지도 설계에 포함.
* 저장 구조(`app_progress.state`, `app_results.detail`/`detail.qa`)와 저장 키(`:vN`)는 **바꾸지 않는다**(학생 기록 유지). 되짚기 이력을 남기려면 기존 구조를 깨지 않는 방법을 제안하고 근거를 적는다.
* SQL이 필요하면 **새 마이그레이션 파일 초안**만 적는다(사용자가 직접 실행). RLS 재귀(42P17) 주의.

## 대상
`public/apps/sci-*` 과학 차시 앱 **전부**(1학기 12개 + 2학기 11개). 실험용 틀 `scripts/templates/science-sim/`(predict.js·conclude.js·persist.js 등)과 조사용 틀 `scripts/templates/science-guide/` 양쪽.
차시별 기준(핵심 낱말·흔한 오개념)은 각 앱 `spec.md`·`data/lesson-config.js`와 지도서에서 뽑는다. **23개 앱 전체의 기준을 spec에 표로 적을 필요는 없고**, 어떻게 뽑을지 방법과 예시(차시 3~4개), 그리고 기준을 앱마다 어디에 두는지(설정 파일 모양)를 정한다.

## 설계에 반드시 담을 것
1. **1안 규칙 검사**: 걸러 낼 유형(너무 짧음, 자음·모음만, 같은 글자 반복, 질문 복사, 숫자만, 무의미한 자판 입력 등)과 차시별 기준(있어야 할 뜻·흔한 오개념 표현). 되짚기 문구 예시(답을 알려 주지 않음). 오탐(맞는데 다시 쓰라고 함)을 줄이는 방법.
2. **2안 Gemini**: Edge Function 이름·입력·출력(JSON 스키마), 프롬프트 초안(한국어, 6학년 눈높이, 두 문장 이내, 답 누설 금지, "괜찮음/다시 생각" 판정), 차시별 채점 기준을 함수가 어떻게 갖는지(앱 설정에서 생성하는 파일 등), 모델 선택(무료 등급), 호출 시점(1안 통과 여부와 관계 — 언제 부르고 언제 건너뛰는지), 시간 제한·재시도·실패 시 1안 전환, 호출 제한(사람별·분당), 비용·한도 추정(한 반 25명 기준).
3. **키 넣는 절차**(사용자가 할 일): 키 발급 → Supabase Secrets 등록 → 함수 배포 → 확인 방법. 명령어까지 정확히.
4. **화면·흐름**: 되짚기 안내가 뜨는 모습, "그대로 제출" 버튼, 기다리는 동안 표시, 오프라인·실패 시 모습. 예상하기와 정리하기 각각.
5. **공통 틀 변경 범위**: 어떤 파일에 무엇을 더하는지(하위 호환 유지, 기준이 없는 앱은 지금과 똑같이 동작).
6. **관리자 쪽 영향**: 되짚기를 몇 번 받았는지 등을 대시보드에서 볼 필요가 있는지(있다면 `detail.qa`를 깨지 않는 방법).
7. **단계별 작업 계획**: 틀 수정 → 앱별 기준 채우기(23개, 나누는 방법) → Edge Function → 검증. 각 단계에서 사용자가 할 일 구분.
8. **열린 질문**(추천안 포함): 예) Gemini를 항상 부를지 1안이 의심할 때만 부를지, 학생 안내 문구, 1학기 앱 포함 여부(사용자는 "전체"라고 했음), 조사 도우미 앱 적용 범위.
