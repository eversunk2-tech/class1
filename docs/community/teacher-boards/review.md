## 2. 확인할 것 1~6 판정

### 1. SQL — 통과(실행은 못 함)
* **문법·이름**: 문장 83개(되돌리기 67개) 괄호 균형·`raise` 자리표시 수·`any ((select` 금지·`search_path=''` 본문 안 이름 모두 이상 없음(제 점검기 — 일부러 넣은 오류 4개는 잡음). 모든 이름 `public.`/`auth.`. 정책 이름 최대 57바이트(옛 78바이트 이름은 drop만 — 같은 규칙으로 잘려 맞음).
* **함수**: 5개 모두 `security definer`·`set search_path = ''`, 만드는 순서 = 부르는 순서(sql 함수 본문은 만들 때 검사). `class_board_owner`는 anon·authenticated 회수지만 `my_board_owner_ids`(소유자 권한으로 실행) 안에서만 불러 문제없음. `select … where …`(FROM 없음) union, 빈 값 거르기 정상. `my_student_class_id()`가 role 'user'·탈퇴 전만 돌려줘 교사·탈퇴 학생에게 학생 갈래가 안 열린다. `is_super_admin()`은 role 'admin' 함께 확인.
* **do 블록 안 열 추가·트리거 끄고 켜기**: plpgsql은 각 문장을 처음 실행할 때 계획하므로 같은 블록에서 새 열을 쓰는 `update`가 가능. 즉시 외래키 검사는 문장마다 끝나 `enable trigger` 때 대기 중인 트리거 없음. 표 소유자(postgres)라 트리거 끄기 권한 있음. `return`으로 재실행 건너뜀 정상.
* **재실행**: 열이 있으면 옮기기 건너뜀(주인 비워진 글도 그대로 — 얼어붙음 유지), 신고 채우기는 빈 값만, 제약·정책 drop 뒤 생성, 열 권한 revoke 뒤 grant(표 단위 revoke가 열 권한도 거둠) → 두 번째 실행도 같은 결과.
* **재귀(42P17) 없음**: 글 정책은 자기 표를 안 읽고 판별 함수는 `profiles`·`class_teachers`만. 댓글·좋아요·신고 정책의 글 하위 쿼리는 다른 표. 배열 비교 `x = any (public.f())` 형식만.
* **권한**: 판별 3개 PUBLIC(비로그인 읽기에도 필요 — 6-10이 확인), `my_boards` authenticated만, `class_board_owner` 내부용, 관리 RPC 4개 옛 권한 그대로(서명·매개변수 이름·기본값 같음 → `create or replace` 가능).
* **이관**: ① 교사 글 → 그 교사 ② 학생 글(탈퇴 포함) → 학급의 먼저 맡은 지금 교사 ③ 나머지 → `v_super`(보관 안 한 학급 담임인 총괄 먼저) ④ 못 채우면 전부 되돌림 · updated_at 보존. 설계 §2.3 ②의 "보관 안 한 학급" 조건은 없지만 보관은 담임이 아무도 안 남을 때만 일어나(`20260927010000:629-632`) 결과가 같다. 실행 전 확인 A가 같은 규칙으로 옮겨 갈 곳을 보여 준다.
* **신고 스냅샷**: 트리거가 글·댓글 신고 모두 `target_post_kind`·`target_board_owner`를 채움(클라이언트는 열 권한 없음), 기존 신고는 (가) 글이 있으면 글에서 (나) 글이 지워진 글·게임 신고는 종류만 → 지워진 옛 댓글 신고만 빈 값(총괄만).
* **맨 끝 점검**: 거짓 실패 경로 없음 — 대상 역할(`본인 수정`·`본인 취소`는 원래 `to authenticated`), 신고 표 UPDATE 권한은 원래 없음(`20260922040000:449-452`), 외래키 점검(6-11)은 ⑦과 같은 조건이고 ⑦은 사용자가 실행·통과(STATUS). 거짓 통과 여지는 L5뿐.
* **되돌리기**: 정책 12·함수 5 본문이 앞선 마이그레이션 "마지막 정의"와 글자 그대로(17/17), 트리거 본문을 먼저 바꾼 뒤 열을 지워 순서 안전, 열을 지우는 까닭(다시 Run 때 재이관) 타당. `docs/classes/rollback-classes-rls.sql`은 ①의 함수를 지우지 않아 함께 써도 충돌 없음. 참고: 되돌린 직후 이미 열려 있던 관리 화면은 새 열을 읽다 "SQL 실행 필요"처럼 보일 수 있다(새로고침하면 예전 동작).
* **완전 삭제(⑦)와 함께**: 옛 교사(담임 해제 뒤 'user') 삭제 → 그 게시판의 남의 글·신고는 주인만 set null(가드 트리거는 게임 파일만 검사, 제약 만족, RI 동작은 RLS·열 권한 무관) → 막히지 않음. 학생은 주인이 될 수 없어 해당 없음. 완전 탈퇴는 `auth.users`만이라 무관.
